SDK Findings — Architecture Impact

What the TypeScript SDK changes about our design. One key constraint to flag.

What Coded Apps Actually Are
Static site hosting on UiPath Automation Cloud. You build a standard React + Vite app. The SDK injects OAuth config via meta tags at deploy time — auth is free, zero custom work. Deploys to https://<org>.uipath.host/<appName>. SDK works in browser — calls Maestro, Tasks, Buckets directly from frontend.
Architecture Simplification

Before (assumed)

Coded App
→ Node.js/Express API
→ UiPath TS SDK
→ Maestro / Buckets / Tasks

Now (simplified)

Coded App (React + Vite)
→ UiPath TS SDK (browser)
→ Maestro / Buckets / Tasks

No separate backend needed. SDK calls UiPath services directly from browser. Future UI swap = different React app or external host, same SDK pattern.

Available Samples (relevant to us)
process-app-v0 Process trigger + monitor — closest to what we need
process-app-v1 Newer version — start here for patterns
conversational-agent-app Agent session management patterns
⚠ Critical Constraint

Coded Apps = Automation Cloud only. No Automation Suite, no Dedicated deployment. If your org runs on-premise or Dedicated, Coded Apps won't work — we'd fall back to Approach B (self-hosted React app + same SDK). Architecture stays identical, only hosting changes.

Future UI Swap Path

Coded App v1 → Custom React app: zero Maestro changes. Just swap the host. Same SDK imports, same service calls, same Maestro process IDs. Works because SDK is browser-native — not tied to UiPath hosting.
